# 壁打ち AI と実装 AI を分けて AWS セキュリティ機能を開発する

AI エージェントにセキュリティ機能の開発を任せるとき、1 つの AI に「設計の相談から実装、テストまで」を一気通貫でやらせると、設計時の思い込みが実装とテストにそのまま伝播する。同じ解釈ミスをしたテストは通ってしまうし、LLM は自分（と同系統のモデル）の出力を高く評価する self-preference bias を持つことが研究で示されている。つまり **作った本人に検収させている** 状態になる。

これに対する実践的な答えが、**壁打ち（設計）役と実装役を別モデルのエージェントに分ける**構成だ。例えば設計壁打ちを Claude（Claude Code）、実装を Codex に割り当てる。この記事は、その構成を AWS セキュリティ機能開発で回すときの設計をまとめる。

ガードレール（アカウント分離・SCP・機械ゲート・人間承認の設計）は [セキュリティ機能開発をAIに任せて人間は承認だけにできるか](./セキュリティ機能開発をAIに任せて人間は承認だけにできるか.md) に書いたので、ここではその上で動く**ワークフローの分割方法**だけを扱う。

---

## なぜ分けるのか — 「2 倍手間」ではなく「検証の独立性」

分ける理由は好みではなく構造的なものだ。

- **生成と検証の独立**。実装した AI と同じモデル・同じコンテキストがレビューやテストを書くと、同じ盲点がそのまま残る。別モデルに分けるのは、フォールトトレランス設計の N-version programming と同じ発想——完全な独立は得られないが、単一系統よりは共通故障が減る
- **self-preference bias の回避**。LLM 評価者は自分の生成物を認識し、人間評価では同等品質でも自分の出力に高いスコアを付ける。レビュー役を実装役と別モデルにするのは、このバイアスの構造的な回避策になる
- **役割ごとの要求が違う**。壁打ちに必要なのは「前提を疑う・脅威を列挙する・トレードオフを言語化する」能力、実装に必要なのは「仕様を忠実にコードへ落とす」能力。フェーズごとに得意なエージェントを割り当てられる

ただし過信しないこと。**別モデルでも学習データは大きく重なっており、独立した検証者ではない。** 「よくある IAM の書き方の穴」のような業界共通の盲点は両方が素通しする。また仕様自体が間違っていれば、両方のモデルが忠実にその間違いを実現する。だから機械ゲートと人間の承認は依然として外せない。

---

## 核心：受け渡しは「チャットの記憶」ではなく「リポジトリ上の成果物」

2 つのエージェントは会話コンテキストを共有できない。これを欠点と捉えて壁打ちのチャットログを実装役に丸ごと渡すと、壁打ち中の思いつき・撤回済みの案・暗黙の前提まで実装役に流れ込む。

そうではなく、**壁打ちの成果を必ず「仕様書」というリポジトリ上の成果物に落とし、実装役にはそれだけを渡す**。仕様書が 2 つの AI の間のコントラクトになる。

セキュリティ機能の仕様書に最低限入れるもの：

- **目的とトリガー**：何の脅威に対する機能か。いつ発火すべきか
- **受け入れ基準を「発火する証拠」で書く**：検知機能なら「この攻撃シミュレーション（例：GuardDuty サンプル検出、テストイベント投入）で検知されること」。「テストが通ること」ではない
- **許可する IAM 権限の上限**：実装役がこれを超える権限を要求してきたら、それ自体がレビュー対象
- **触ってよいリソースの範囲**と**ロールバック手段**
- **やらないこと**：スコープ外を明記しないと、実装 AI は気を利かせて余計なものを作る

この方式には副産物がある。仕様書・実装 PR・レビュー結果がすべてリポジトリに残るので、**「AI に任せた開発」の監査証跡がそのまま揃う**。チャット駆動で開発すると、この証跡が一番先に失われる。

両エージェントへの共通指示（リポジトリ構成、テストコマンド、コーディング規約、触ってはいけない場所）は `CLAUDE.md` と `AGENTS.md` の両方に同じ内容で整備する。片方だけ更新して指示が食い違うのが典型的な事故なので、片方を実体・もう片方をシンボリックリンクにするか、CI で差分検知する。

## 開発ループの全体像

```
Phase 1  壁打ち（例：Claude）
         要件の言語化・脅威モデル・既存構成との整合確認
         → 成果物：仕様書の PR
         → ★人間が仕様を承認（ここが人間の主要な介入点）

Phase 2  実装（例：Codex）
         仕様書を入力に、sandbox 向けの IaC＋コードを実装
         → 成果物：実装 PR（攻撃シミュレーションによる発火証拠付き）

Phase 3  クロスレビュー（例：Claude）
         実装 PR を仕様書と突合。特に：
         - 仕様にない IAM 権限・リソースが増えていないか
         - 受け入れ基準（発火証拠）を満たしているか
         - 「テストを通すためのテスト」になっていないか

Phase 4  機械ゲート → 人間のリスクベース承認 → パイプラインでデプロイ
         （ここは既存記事のレイヤー設計の通り）
```

運用上の要点：

- **人間の介入を仕様承認（Phase 1 の出口）に集中させる**。仕様が正しければ、以降のフェーズは機械ゲートとクロスレビューで大半を吸収できる。逆に仕様承認を流し読みすると、後段の全てが「間違った仕様の忠実な実現」を検証するだけになる
- **壁打ちの終了条件を「仕様書の PR が出ること」にする**。壁打ちで一番多い失敗は、議論が盛り上がって結論がチャットに残ったまま終わること。成果物が出ない壁打ちは未完了として扱う
- **クロスレビューでの指摘は仕様書に還流する**。実装役とレビュー役の意見が割れたら、AI 同士で往復させ続けない（収束しないピンポンはコストだけ食う）。往復は 2 回までと決め、割れたまま残った論点は人間が裁定して仕様書を更新する

## AWS 上で動かすときの追加設計

ガードレールの全体像は既存記事に譲り、2 エージェント構成に固有の点だけ挙げる。

**実装役に AWS 認証情報を直接渡さないのが基本形。** 実装役の仕事は「IaC とコードを書いて PR を出す」まで、sandbox への適用は CI パイプラインのロール（OIDC の短命トークン）が行う。実装エージェント自体の実行環境（Codex cloud の環境や CI ランナー）に AWS の長期キーを置く構成は避ける。デバッグのために実行時アクセスがどうしても必要なら、sandbox アカウント限定・短命・read 中心のロールを別途切る。

**2 つのエージェントの権限を非対称にする。** 壁打ち役に必要なのは既存構成の調査なので read-only（`ReadOnlyAccess` ベースからさらに絞る）で足りる。write 系が必要なのは実装役のパイプラインだけ。役割を分けた意味を IAM にもそのまま反映する。

**エージェントごとに別のロール・別のベースラインで監視する。** 壁打ち役のロールが write API を呼んだら、それ自体が異常検知の対象になる。役割分割は監視の解像度を上げる道具にもなる。

## いつ使うか — 全部にこの体制は過剰

2 モデル体制は往復コストがかかる。リスクベースで使い分ける。

| 変更の種類 | 体制 |
|---|---|
| 検知ルールの閾値調整、タグ付与などの低リスク変更 | 単一エージェント＋機械ゲートで十分 |
| 新しい検知機能、Lambda を伴う自動化 | 壁打ち→仕様書→実装の分割を推奨 |
| IAM・SCP・自動修復（enforce）など壊れると痛い変更 | 分割＋クロスレビュー＋人間 2 名承認を必須に |

### ビジネス側への言語化

| 技術的な言い方 | ビジネス側に刺さる言い方 |
|---|---|
| 設計 AI と実装 AI を別モデルに分ける | 作った本人に検収させない、という当たり前の職務分離を AI にも適用する |
| 受け渡しを仕様書ベースにする | AI に任せた開発の判断過程が全部文書で残り、監査にそのまま出せる |
| 人間の承認を仕様承認に集中させる | 人間は全 PR を眺める係ではなく、「何を作るか」の意思決定に時間を使える |
