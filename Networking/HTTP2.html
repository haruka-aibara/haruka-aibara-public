HTTP/2

どういうときに困るのか

ページの表示が遅い。調べると1リクエストあたりの応答は速いのに、画像・CSS・JS が数十個あって全体が遅い。HTTP/1.1 では1つの TCP コネクションで同時に1リクエストしか処理できず、前のレスポンスが返るまで次が待たされる（Head-of-Line ブロッキング）。ブラウザは仕方なくドメインあたり6本程度のコネクションを張るが、それでも足りない。

回避策として、画像を1枚に結合する CSS スプライト、JS/CSS のバンドル、静的ファイルを別ドメインに逃がすドメインシャーディングが使われてきた。これらは「HTTP/1.1 の制約を迂回するためのハック」であって、本来必要ない作業。

その制約を、プロトコル側で解決したのが HTTP/2。

何が変わったのか

1. バイナリフレーム

HTTP/1.1 のテキスト形式をやめ、フレームという固定構造の単位に分割して送る。ヘッダは HEADERS フレーム、ボディは DATA フレーム。パースが機械的になり、多重化の土台になる。

2. ストリームの多重化（本命）

1本の TCP コネクション上に、ストリームという論理的な通信路を複数並べる。各フレームはストリーム ID を持つので、複数のリクエスト／レスポンスを同時並行でやり取りできる。順番待ちが消える。

結果として、スプライト画像もドメインシャーディングも不要になる。むしろシャーディングはコネクションを分散させて HTTP/2 の利点を潰すので逆効果。

3. ヘッダ圧縮（HPACK）

Cookie や User-Agent は毎リクエストほぼ同じ内容が繰り返される。HPACK は静的テーブル＋動的テーブルで既出のヘッダをインデックス参照に置き換え、リクエストあたり数百バイトの重複を削る。リクエスト数が多いページほど効く。

4. ストリーム優先度

「CSS を画像より先に」といった重み付けをクライアントが指定できる。ただし実装差が大きく、RFC 9113 では優先度スキームは非推奨扱いになった。

5. サーバプッシュ

HTML を返すついでに CSS も送りつける機能。キャッシュ済みのものを送って無駄になるケースが多く、Chrome は 2022 年にデフォルト無効化。実質的に死んだ機能で、103 Early Hints が代替。

運用上のポイント

  • 実質 TLS 必須：仕様上は平文（h2c）も可能だが、主要ブラウザは TLS 上でしかサポートしない。ネゴシエーションは TLS 拡張の ALPN で行う。
  • TCP レベルの HoL は残る：HTTP のブロッキングは解消したが、TCP パケットが1つ落ちると全ストリームが待たされる。ここを潰したのが QUIC（UDP ベース）上に載る HTTP/3。
  • HTTP/1.1 向け最適化を消す：シャーディングやインライン化は残っていると足を引っ張る。
  • 導入は端点だけで済むことが多い：ALB / CloudFront / nginx などのフロント側で HTTP/2 を有効にすれば、バックエンドは HTTP/1.1 のままでよい。

セキュリティ視点

多重化は「1コネクションで大量のリクエストを投げられる」ことでもあり、DoS の増幅要因になる。実例：

  • HTTP/2 Rapid Reset（CVE-2023-44487）：リクエスト直後に RST_STREAM でキャンセルする動作を繰り返し、同時ストリーム上限を回避してサーバを飽和させる。2023 年に観測史上最大級の DDoS に使われた。対策はサーバ／ミドルウェアのパッチ適用とストリームリセットのレート制限。
  • リクエストスマグリング：フロントが HTTP/2、バックエンドが HTTP/1.1 という構成では、ダウングレード変換時のヘッダ解釈差が悪用されうる（H2.CL / H2.TE）。

提案するときの言い方：「HTTP/2 は表示速度の改善策だが、同時に1コネクションあたりの負荷特性が変わる。WAF やレート制限の閾値がリクエスト数前提なら、見直しが要る」。
