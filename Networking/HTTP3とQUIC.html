HTTP/3 と QUIC

この判断を迫られるとき

HTTP/3 を自分から調べにいく人は少ない。だいたい次のどれかで踏むことになる。

  • CloudFront の設定画面に「HTTP/3」のトグルがあり、入れるべきか判断がつかない
  • ファイアウォールで UDP/443 を開けてほしいと依頼が来て、通していいのか聞かれた
  • ネットワーク側の検査装置に出てこない通信があり、調べたら QUIC だった

つまりトリガーは「学びたい」ではなく「有効にするか / 通すか」の判断を求められたとき。この記事はそこに答える形で書く。

なぜ HTTP/2 では足りなかったのか

問題 1: パケットが 1 つ落ちると全部止まる。 HTTP/2 は 1 本の TCP コネクションに複数ストリームを多重化する。だが TCP は順序保証をするので、パケットが 1 つ落ちるとその再送が届くまで後続の全ストリームがまとめて止まる。画像の 1 パケットが落ちて CSS の描画まで止まる。アプリ層で多重化しても、下の TCP がボトルネックになる。これが TCP Head-of-Line ブロッキング。

問題 2: IP が変わると切れる。 TCP コネクションは「送信元 IP:ポート / 宛先 IP:ポート」で識別される。電車で Wi-Fi からモバイル回線に切り替わると IP が変わり、コネクションは別物として扱われ、TLS ハンドシェイクからやり直しになる。

どちらも TCP そのものの性質なので、HTTP 側をいくら改良しても解けない。ではなぜ TCP を直さないのか——TCP はカーネル実装で、かつ中間機器（NAT・FW・ロードバランサ）がヘッダを読んで挙動を変えているため、事実上もう仕様を変えられない。

QUIC が変えたこと

そこで UDP の上に、TCP + TLS 1.3 相当を作り直したのが QUIC（RFC 9000）。UDP は「ポート番号が付いただけの IP」なので、その上に信頼性・輻輳制御・暗号化を自前で実装できる。しかもカーネルではなくユーザー空間（＝ブラウザとサーバーのアップデートだけ）で完結する。

変えたこと効果
ストリームごとに独立して順序保証ロスの影響が落ちたストリームだけに閉じる（問題 1 が解ける）
コネクションを Connection ID で識別IP が変わっても接続を継続（問題 2 が解ける）
トランスポートと TLS のハンドシェイクを統合2-RTT → 1-RTT。再訪問なら 0-RTT
ヘッダまで含めてほぼ全体を暗号化中間機器がいじれない＝今後も仕様を変えられる

その QUIC の上に HTTP を載せたものが HTTP/3（RFC 9114）。HTTP のセマンティクス（メソッド、ステータスコード、ヘッダ）は HTTP/2 と同じで、変わったのは運び方だけ。アプリケーションのコードは書き換え不要。

効く場面と、効かない場面

「新しいから入れる」で判断しない。QUIC が解いた 2 つの問題はロスがあり RTT が大きい経路にしか存在しない。

効く効かない（むしろ損）
モバイル回線・海外リージョンからのアクセスなど、RTT が大きくロスが出る経路データセンター内・同一 VPC 内の通信。ロスがほぼ無いので HoL ブロッキングが起きない
移動しながら使われるクライアント（スマホアプリ、モバイルブラウザ）サーバー間 API 通信。IP は変わらないしハンドシェイクも使い回している

加えて、TCP はカーネル処理と NIC オフロードの恩恵を受けるが、QUIC はユーザー空間実装なのでパケット処理の CPU コストが乗る。低 RTT の環境で HTTP/3 にすると、速くならずに CPU だけ増えることがある。エンドユーザー向けの配信では入れる、内部通信では入れない、が基本線。

有効にしたのに h3 にならない

ブラウザはいきなり UDP では来ない。まず HTTP/1.1 か HTTP/2 で接続し、レスポンスヘッダの Alt-Svc を見て「次からは HTTP/3 で来い」と学習する。

Alt-Svc: h3=":443"; ma=86400

したがって初回アクセスは必ず HTTP/3 にならない。「設定したのに DevTools で h3 と出ない」の大半はこれで、リロードすれば切り替わる。それでも変わらない場合は UDP/443 が経路で落とされている。

セキュリティ・監視への影響

実務で一番効いてくるのは速度ではなく、ネットワーク側の可視性が落ちること。

  • IDS/IPS・DPI が中身を読めない：TCP はヘッダが平文なので中間点から状態を追えたが、QUIC はヘッダごと暗号化されている。キャプチャしても「UDP のバイト列」しか見えず、既存のネットワーク検知ルールは QUIC トラフィックに効かない
  • 可視性はエンドポイント側に移す：見る場所をネットワーク中間点から、CloudFront / ALB のアクセスログ、WAF ログ、サーバーのアプリログへ寄せる。HTTP/3 を有効にする作業とセットで必要
  • egress の抜け道になり得る：正規の Web 通信と区別しづらい UDP/443 は、外部への持ち出し経路として悪用されやすい。外向き通信を絞っている環境では QUIC を通すかどうかを明示的に決める
  • 塞いでも壊れない：UDP/443 を落としてもブラウザは TCP にフォールバックする。「速度を捨てて可視性を取る」という選択肢が実際に成立する。ただし黙って塞ぐと「なぜか遅い」の原因調査に時間を溶かすので、判断として記録に残す

提案するときの言い方

技術的な言い方ビジネス側に刺さる言い方
CloudFront で HTTP/3 を有効化するモバイル回線や海外からのアクセスの表示速度が上がる。アプリの改修は不要で、設定 1 つで済む
QUIC はヘッダまで暗号化されるこれまでネットワーク機器で見ていた通信内容が見えなくなる。監視をサーバー側のログに移す作業が必要になる
egress で UDP/443 の扱いを決める社内から外部へデータを持ち出す新しい経路が増える。通すか塞ぐかを決めずに放置するのが一番まずい

実際の設定

自前でサーバーを立てる場面は少なく、CDN / ロードバランサ側の設定になる。

  • CloudFront：ディストリビューションの「サポートされている HTTP バージョン」で HTTP/3 を選ぶ。Alt-Svc は自動で付く
  • ALB：非対応。QUIC を通したいなら前段に CloudFront を置くか、NLB の UDP リスナー＋自前サーバー
  • nginx：1.25.0 以降。listen 443 quic reuseport; を足し、Alt-Svc は add_header で自分で付ける
