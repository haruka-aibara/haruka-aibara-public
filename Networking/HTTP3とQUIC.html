HTTP/3 と QUIC

どういうときに困るのか

モバイル回線でサイトを開くと、Wi-Fi では速いのに 4G だと妙に重い。パケットロスが数％あるだけで、画像も CSS も JS も同時に止まる。HTTP/2 は 1 本の TCP コネクションに複数ストリームを多重化するので、TCP レイヤで 1 パケット落ちると、後続の全ストリームが再送待ちで止まる（TCP Head-of-Line ブロッキング）。アプリ層で多重化しても、下の TCP が順序保証をする限り逃げられない。

もう一つ。電車で Wi-Fi からモバイル回線に切り替わると通信が切れる。TCP コネクションは「送信元 IP:ポート / 宛先 IP:ポート」の 4 つ組で識別されるので、IP が変わればコネクションは別物になり、TLS ハンドシェイクからやり直しになる。

この 2 つを解決するのが QUIC で、その上に載せた HTTP が HTTP/3。

QUIC とは

UDP の上に、TCP + TLS 1.3 相当の機能をユーザー空間で実装したトランスポートプロトコル（RFC 9000）。UDP を選んだのは速いからではなく、TCP がカーネル実装かつ中間機器に深く根付いていて、もう仕様を変えられないから。UDP は「ポート番号だけ付いた IP」なので、その上に自前で信頼性・輻輳制御・暗号化を作れる。

1. ストリームごとの独立した順序保証

QUIC は複数ストリームを持ち、ロスの影響が落ちたパケットのストリームだけに閉じる。画像のパケットが落ちても CSS の描画は進む。HTTP/2 が解けなかった HoL ブロッキングがここで解ける。

2. Connection ID による接続維持

コネクションを IP:ポートではなく Connection ID で識別する。Wi-Fi → モバイルで IP が変わっても、同じ Connection ID なら同じ接続として継続（コネクションマイグレーション）。ハンドシェイクのやり直しが起きない。

3. ハンドシェイクが 1-RTT / 0-RTT

TCP + TLS 1.3 は「TCP 3ウェイ（1-RTT）＋ TLS（1-RTT）」で最低 2-RTT。QUIC はトランスポートと TLS のハンドシェイクを統合して 1-RTT、再訪問なら 0-RTT（最初のパケットにデータを載せる）。RTT が大きいモバイル・遠距離ほど効く。

4. 暗号化の範囲が広い

TCP はヘッダが平文なので、中間機器がシーケンス番号を見て挙動を変えられた（それが TCP を進化できなくした原因でもある）。QUIC はペイロードだけでなくトランスポートヘッダのほぼ全体を暗号化する。中間機器から中身が見えない＝勝手にいじられない＝将来仕様を変えられる。

どうやって HTTP/3 に切り替わるか

ブラウザはいきなり UDP で来ない。まず HTTP/1.1 か HTTP/2 で接続し、レスポンスヘッダの Alt-Svc を見て「次からは HTTP/3 で来い」と学習する。

Alt-Svc: h3=":443"; ma=86400

つまり 初回アクセスは HTTP/3 にならない。「有効にしたのに Chrome DevTools で h3 にならない」の大半はこれで、リロードすれば h3 になる。

運用で引っかかるところ

  • UDP/443 が閉じている：企業ファイアウォールやプロキシは UDP/443 をデフォルトで落とすことが多い。この場合ブラウザは TCP にフォールバックするので「壊れない代わりに速くならない」。導入したのに効果が出ないときはまずここを疑う。
  • CPU 負荷が高くなりがち：TCP はカーネル・NIC オフロードの恩恵を受けるが、QUIC はユーザー空間実装なのでパケット処理コストが乗る。低 RTT・低ロスのデータセンター内通信では HTTP/3 にしても速くならず、CPU だけ増えることがある。効くのは RTT が大きくロスがある経路（＝エンドユーザー向け）。
  • UDP リフレクション対策：QUIC はハンドシェイク中、クライアントの初期パケットに 1200 バイト以上のパディングを要求し、サーバーの応答量を制限する（増幅攻撃の緩和）。設定でここを緩めない。

セキュリティ・監視の観点

ネットワーク側の可視性が下がるのが最大の実務インパクト。

  • IDS/IPS・DPI が中身を見られない：TCP ならヘッダから状態を追えたが、QUIC は暗号化されているため、パケットキャプチャからは「UDP のバイト列」しか見えない。既存のネットワーク検知ルールは QUIC トラフィックに効かない。
  • ログはエンドポイント側で取る：可視性をネットワーク中間点からサーバー側（ALB / CloudFront のアクセスログ、WAF ログ）に寄せる必要がある。
  • ブロックすればフォールバックする：可視性を優先する環境では UDP/443 を落とす判断もあり得る。ブラウザは TCP に戻るので通信自体は壊れない。ただし「速度を捨てて可視性を取る」という明示的な選択であることを認識しておく。
  • C2 通信の隠れ蓑になり得る：正規の Web トラフィックと区別しづらい UDP/443 は、外部通信の抜け道として悪用されやすい。egress を絞る設計なら QUIC の扱いを決めておく。
ビジネス側への言い方：「HTTP/3 はモバイルユーザーの体感速度を改善する。ただし通信が全部暗号化されるので、これまでネットワーク機器で見ていた通信内容が見えなくなる。監視をサーバー側のログに移す作業がセットで必要」

マネージドサービスでの有効化

自前でサーバーを立てる場面は少なく、実務では CDN / ロードバランサ側の設定になる。

  • CloudFront：ディストリビューションの「サポートされている HTTP バージョン」で HTTP/3 を有効化。Alt-Svc は自動で付与される。
  • ALB：非対応（TCP ベース）。QUIC を通したい場合は NLB の UDP リスナー＋自前サーバー、または CloudFront を前段に置く。
  • nginx：1.25.0 以降で listen 443 quic reuseport; と Alt-Svc ヘッダの手動付与。
