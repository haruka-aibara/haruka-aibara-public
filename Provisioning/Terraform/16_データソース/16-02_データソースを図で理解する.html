データソース（data）を図で理解する

Terraform が「知らない」リソースを、壊さずに読み取るための仕組み。

何が問題なのか

Terraform は自分が管理しているリソースしか知らない。でも現実には、管理外のリソースを参照したい場面がたくさんある——ネットワークチームが管理している VPC、コンソールで手作業で作られた Route53 ホストゾーン、AWS 側が更新し続けている最新の AMI。

それを解決するのが data ブロック。作成も変更も削除もせず、読み取るだけ。

参照したいというだけで resource に書いてしまうと、Terraform はそれを自分の持ち物だと解釈する。他チームのリソースを上書きしたり、destroy で消したりできてしまう。data はそこを構造的に分ける。

書き方

data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id   # ハードコードしなくて済む
  instance_type = "t3.micro"
}

参照は data.タイプ.名前.属性。resource の参照（タイプ.名前.属性）に data. が前置される形。

いつ読まれるのか

「plan に (known after apply) が並んで、何が変わるのか読めない」——これの原因はたいてい data の読み取りタイミングにある。

Terraform は data をできるだけ plan 時に読もうとする。ただし引数に「plan の時点で確定していない値」が混じっていると、読み取りが apply まで先送りされる。

どれを使うか

data か resource かで迷うことは少ないが、import や terraform_remote_state とは境界が曖昧になりやすい。

よく使う場面

別チームが管理しているリソースを使う

data "aws_subnets" "shared_private" {
  filter {
    name   = "tag:Name"
    values = ["shared-private-*"]
  }
}

resource "aws_ecs_service" "app" {
  network_configuration {
    subnets = data.aws_subnets.shared_private.ids
  }
}

タグで引くのがポイント。ID をハードコードすると、相手側がリソースを作り直したときに黙って壊れる。

実行中のアカウント・リージョンを埋め込む

data "aws_caller_identity" "current" {}
data "aws_region" "current" {}

resource "aws_s3_bucket" "logs" {
  bucket = "logs-${data.aws_caller_identity.current.account_id}-${data.aws_region.current.region}"
}

同じコードを dev / prod の別アカウントに適用しても、バケット名が自動で分かれる。

AWS プロバイダ v6 での変更

data.aws_region.current.name は v6.0 で非推奨になり、.region に置き換わった。v7 での削除が予告されている。プロバイダを上げたときに大量の deprecation warning が出るのはこれ。

IAM ポリシーを JSON 直書きせずに組み立てる

data "aws_iam_policy_document" "s3_read" {
  statement {
    actions   = ["s3:GetObject"]
    resources = ["${aws_s3_bucket.logs.arn}/*"]
  }
}

resource "aws_iam_role_policy" "app" {
  policy = data.aws_iam_policy_document.s3_read.json
}

これは外部を読みに行かない「ローカル完結型」の data。API を呼ばず、HCL を JSON に変換するだけ。jsonencode() と違って構文チェックが効き、複数ポリシーの合成（source_policy_documents）もできる。

ハマりどころ

  • 見つからないとエラーで止まる：data はマッチしないと no matching X found で plan ごと失敗する。null は返らないし try() でも握りつぶせない——エラーは式の評価ではなく読み取りの時点で起きるため。存在が不確実なものを参照したいなら、count で読み取り自体をスキップする。
  • 複数マッチしてもエラー：aws_ami や aws_subnet のような単数形は「ちょうど1件」を要求する。フィルタが緩いと、リソースが増えた日に突然壊れる。複数前提なら aws_subnets のような複数形を使う。
  • モジュールを呼ぶ数だけ API が叩かれる：モジュール内に data "aws_ami" を置いて 30 回呼べば、plan のたびに 30 回リクエストが飛ぶ。plan が遅い・スロットリングされる場合はここを疑い、ルート側で一度読んで変数で渡す。

most_recent = true は「変更のトリガー」でもある

最新 AMI を自動で拾う書き方は便利だが、管理外の出来事が自分の plan を動かすということでもある。

セキュリティ視点

data の読み取り結果は state に平文で書かれる。属性に sensitive が付いていてもそれは CLI 出力のマスクであって、state ファイルの中身は隠れない。

つまり data "aws_secretsmanager_secret_version" でパスワードを取得した瞬間、state バケットを読める人全員がそのパスワードを読めるようになる。Terraform 1.10 の ephemeral はここを塞ぐために入った。

もうひとつ、権限設計にも影響する。data はプロバイダの API を叩くので、plan を回すだけでも読み取り権限が要る。CI で plan と apply のロールを分けるとき、plan 側を「権限ゼロ」にはできない——data が触る範囲の Describe* / Get* が必要になる。逆に言えば、plan 用ロールは読み取り専用で足りるので、PR 時点では書き込み権限を一切渡さない設計が成立する。

技術的な言い方ビジネス側に刺さる言い方
秘密は data ではなく ephemeral で読むstate ファイルを一度でも取られたら DB パスワードごと流出する。そこを構造的に断つ
plan 用ロールを読み取り専用に分離するPR のレビュー段階では、AI もエンジニアも本番を変更する権限を一切持たない状態にできる
他チームのリソースは resource ではなく data で参照する設定ミス1つで他チームの本番を消す、という事故の経路をなくす
