データソース（data）を図で理解する

Terraform が「知らない」リソースを、壊さずに読み取るための仕組み。

何が問題なのか

Terraform は自分が管理しているリソースしか知らない。でも現実には、管理外のリソースを参照したい場面がたくさんある——ネットワークチームが管理している VPC、コンソールで手作業で作られた Route53 ホストゾーン、AWS 側が更新し続けている最新の AMI。

それを解決するのが data ブロック。作成も変更も削除もせず、読み取るだけ。

参照したいというだけで resource に書いてしまうと、Terraform はそれを自分の持ち物だと解釈する。他チームのリソースを上書きしたり、destroy で消したりできてしまう。data はそこを構造的に分ける。

書き方

data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id   # ハードコードしなくて済む
  instance_type = "t3.micro"
}

参照は data.タイプ.名前.属性。resource の参照（タイプ.名前.属性）に data. が前置される形。

タグで引く

data "aws_subnets" "shared_private" {
  filter {
    name   = "tag:Name"
    values = ["shared-private-*"]
  }
}

他チームのリソースを参照するときは ID をハードコードせず、タグで引く。ID 直書きだと相手がリソースを作り直した瞬間に黙って壊れる。

アカウント・リージョンを埋め込む

data "aws_caller_identity" "current" {}
data "aws_region" "current" {}

resource "aws_s3_bucket" "logs" {
  bucket = "logs-${data.aws_caller_identity.current.account_id}-${data.aws_region.current.region}"
}

同じコードを dev / prod の別アカウントに適用しても、バケット名が自動で分かれる。

AWS プロバイダ v6 での変更

data.aws_region.current.name は v6.0 で非推奨になり、.region に置き換わった。プロバイダを上げたときに大量の deprecation warning が出るのはこれ。

いつ読まれるのか

「plan に (known after apply) が並んで、何が変わるのか読めない」——これの原因はたいてい data の読み取りタイミングにある。

Terraform は data をできるだけ plan 時に読もうとする。ただし引数に「plan の時点で確定していない値」が混じると、読み取りが apply まで先送りされる。

ハマりどころ

  • 見つからないとエラーで止まる：マッチしないと no matching X found で plan ごと失敗する。null は返らないし try() でも握りつぶせない——エラーは式の評価ではなく読み取りの時点で起きるため。存在が不確実なら count で読み取り自体をスキップする。
  • 複数マッチしてもエラー：aws_ami や aws_subnet のような単数形は「ちょうど1件」を要求する。フィルタが緩いと、リソースが増えた日に突然壊れる。複数前提なら aws_subnets のような複数形を使う。
  • 読み取り結果は state に平文で残る：sensitive は CLI 出力のマスクであって、state の中身は隠れない。data "aws_secretsmanager_secret_version" でパスワードを読めば、state バケットを読める人全員がそれを読める。秘密は data ではなく ephemeral（Terraform 1.10+）で扱う。→ 22-05 シークレット管理

most_recent = true は「変更のトリガー」でもある

最新 AMI を自動で拾う書き方は便利だが、管理外の出来事が自分の plan を動かすということでもある。
