# ログ集約サーバーの構築

インシデント対応でホストに入ったら、調べたいログが消えていた。侵害されたホストのログはそもそも信用できないし、ディスクが埋まって古いログが消えていることもある。

**ログは生成された瞬間に、そのホストの外へ出す。** ここでは rsyslog / syslog-ng で集約サーバーを立てる手順と、監査に耐える構成にするための設計を扱う。

## 何を守る構成なのか

「ログを集める」を実装に落とすと、最低限これだけの性質が要る。

| 要件 | 実装 |
|---|---|
| 経路上で盗聴・改ざんされない | TLS（6514）＋ サーバー証明書検証 |
| 送信元を詐称されない | クライアント証明書による相互認証 |
| ネットワーク断でも欠損しない | 送信側のディスクバッファ＋無限リトライ |
| 侵害されたホストから消せない | 集約先を別の権限境界に置き、削除権限を与えない |
| 時系列が突き合わせられる | 全ホストで NTP 同期、RFC 5424（タイムゾーン付き） |

このうち**最後の 2 つが抜けている構成をよく見る**。集約サーバーの root 鍵を全ホストに配っていたり、ホスト間で時刻が数分ずれていたりすると、集めた意味が半分なくなる。

## rsyslog：受信側

```
# /etc/rsyslog.d/10-server.conf

# TLS 証明書（gtls ドライバは rsyslog-gnutls パッケージが必要）
global(
  DefaultNetstreamDriver="gtls"
  DefaultNetstreamDriverCAFile="/etc/pki/rsyslog/ca.pem"
  DefaultNetstreamDriverCertFile="/etc/pki/rsyslog/server-cert.pem"
  DefaultNetstreamDriverKeyFile="/etc/pki/rsyslog/server-key.pem"
)

# クライアント証明書を必須にする（x509/name で CN も検証）
module(load="imtcp"
       StreamDriver.Name="gtls"
       StreamDriver.Mode="1"
       StreamDriver.AuthMode="x509/name"
       PermittedPeer=["*.example.internal"])
input(type="imtcp" port="6514")

# ホスト別・プログラム別にファイルを分ける
template(name="RemoteFile" type="string"
         string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")

if $fromhost-ip != "127.0.0.1" then {
    action(type="omfile" dynaFile="RemoteFile"
           fileCreateMode="0600" dirCreateMode="0700"
           fileOwner="root" fileGroup="root")
    stop
}
```

`stop` を入れないと、受信したリモートログが集約サーバー自身の `/var/log/messages` にも二重に書かれる。

ファイル名に `%HOSTNAME%` を使う場合、**ホスト名は送信側の自己申告**である点に注意。詐称を許さないなら `%FROMHOST-IP%` を使うか、上の `PermittedPeer` のように証明書の CN で縛る。

設定を書いたら文法チェックしてから再起動する。

```bash
sudo rsyslogd -N1                 # 文法チェック
sudo systemctl restart rsyslog
```

RHEL 系は SELinux が 6514 を塞ぐので、ポートを許可しておく。

```bash
sudo semanage port -a -t syslogd_port_t -p tcp 6514
sudo firewall-cmd --add-port=6514/tcp --permanent && sudo firewall-cmd --reload
```

## rsyslog：送信側

**ここでの本題はディスクバッファ**。集約サーバーが落ちている間やネットワークが切れている間のログを、復旧後に送り直すための設定になる。これがないと、障害中という一番知りたい時間帯のログが丸ごと消える。

```
# /etc/rsyslog.d/90-forward.conf

global(
  DefaultNetstreamDriver="gtls"
  DefaultNetstreamDriverCAFile="/etc/pki/rsyslog/ca.pem"
  DefaultNetstreamDriverCertFile="/etc/pki/rsyslog/client-cert.pem"
  DefaultNetstreamDriverKeyFile="/etc/pki/rsyslog/client-key.pem"
)

*.* action(type="omfwd"
           target="logs.example.internal" port="6514" protocol="tcp"
           StreamDriver="gtls" StreamDriverMode="1"
           StreamDriverAuthMode="x509/name"
           StreamDriverPermittedPeers="logs.example.internal"
           template="RSYSLOG_SyslogProtocol23Format"

           # ディスク支援キュー：メモリが溢れたらディスクへ退避
           queue.type="LinkedList"
           queue.filename="fwd_central"
           queue.spoolDirectory="/var/spool/rsyslog"
           queue.maxDiskSpace="1g"
           queue.saveOnShutdown="on"

           # 送信先が復帰するまで諦めずに再送する
           action.resumeRetryCount="-1"
           action.resumeInterval="10")
```

要点は 3 つ。

- `template="RSYSLOG_SyslogProtocol23Format"` で RFC 5424 形式にする。**これを付けないとタイムゾーンなしの古い形式**で送られる
- `queue.saveOnShutdown="on"` で、再起動時に未送信分をディスクへ書き出す。これがないと再起動でキューが消える
- `action.resumeRetryCount="-1"` は無限リトライ。既定値では数回で諦めてログを捨てる

`queue.maxDiskSpace` はディスクを食い潰さないための上限。**このサイズが、集約サーバーの停止に何時間耐えられるかを決める**ので、ログ流量から逆算して決める。

## syslog-ng の場合

同じ構成を syslog-ng で書くとこうなる。

**受信側：**

```
source s_net {
  syslog(transport("tls") port(6514)
    tls(key-file("/etc/syslog-ng/server-key.pem")
        cert-file("/etc/syslog-ng/server-cert.pem")
        ca-dir("/etc/syslog-ng/ca.d")
        peer-verify(required-trusted)));
};

destination d_hosts {
  file("/var/log/remote/${HOST}/${PROGRAM}.log"
       create-dirs(yes) dir-perm(0700) perm(0600));
};

log { source(s_net); destination(d_hosts); };
```

**送信側：**

```
destination d_central {
  syslog("logs.example.internal" transport("tls") port(6514)
    tls(key-file("/etc/syslog-ng/client-key.pem")
        cert-file("/etc/syslog-ng/client-cert.pem")
        ca-dir("/etc/syslog-ng/ca.d")
        peer-verify(required-trusted))
    disk-buffer(disk-buf-size(1073741824) mem-buf-size(1048576) reliable(yes)
                dir("/var/lib/syslog-ng/disk-buffer")));
};

log { source(s_system); source(s_journald); destination(d_central); };
```

`reliable(yes)` は、メッセージをディスクへ書いてから次へ進む設定。プロセスが落ちても失わない代わりにスループットは落ちる。監査ログなら `yes`、大量のアクセスログなら `no` と使い分ける。

検証コマンドは以下。

```bash
sudo syslog-ng --syntax-only        # 文法チェック
sudo syslog-ng-ctl stats            # 経路ごとの処理・破棄件数
```

`syslog-ng-ctl stats` の `dropped` が増えていないかは、構築後に必ず見る。ここが増えていると、動いているように見えて実は捨てられている。

## 疎通と欠損の確認

構築直後に、正常系と異常系の両方を試す。

```bash
# 送信側で 1 行流し、集約サーバー側にファイルができるか見る
logger -p local0.info "syslog forwarding test"

# 異常系：集約サーバーを止めた状態でログを流し、
# 送信側にスプールが溜まるか → 復旧後に届くかを確認する
ls -lh /var/spool/rsyslog/
```

**この異常系のテストをやらないと、バッファ設定が効いているかは分からない**。設定を書いただけで動いていない（ディレクトリのパーミッションや SELinux で書けていない）ことは珍しくない。

## セキュリティ設計としての置き場所

技術的に転送できることと、**インシデント時に証拠として使えること**は別問題になる。

**集約先は、送信元とは別の権限境界に置く。** 同じ AWS アカウント・同じ管理者権限の下に置くと、あるホストを取られた時点で集約サーバーにも到達され、ログを消される。実装としては、ログ集約用のアカウント（あるいは最低でも別 VPC・別の IAM 権限）に置き、**送信側には書き込み権限だけを与えて削除・上書きをさせない**。

**長期保全は Object Lock に寄せる。** ファイルとして持ち続ける限り、集約サーバーの root を取られれば消せる。ローテーション後に S3 へ退避し、Object Lock（コンプライアンスモード）を掛ければ、権限を持つ者でも保持期間中は削除できない。監査・訴訟対応で求められるのはこの性質になる。

**時刻同期を先に済ませる。** chrony が全ホストで動いていること。数分のずれがあると、複数ホストにまたがる攻撃の順序が追えなくなる。集約の前提条件として扱う。

### 提案するときの言い方

構築を通すには、技術的な正しさとは別の説明が要る。

| 技術的な言い方 | ビジネス側に刺さる言い方 |
|---|---|
| syslog を TLS で集約サーバーへ転送する | 侵害されたサーバーの中のログは犯人に消せる。消される前に手の届かない場所へ写しておく |
| ディスクバッファを設定する | ネットワークが切れていた時間帯 = 障害が起きていた時間帯のログが、設定なしでは残らない |
| S3 に Object Lock を掛ける | 監査や訴訟で「このログは改ざんされていない」と示せる状態にしておく |
| NTP を全ホストで同期する | 時計がずれていると「どのサーバーが先に侵入されたか」が特定できず、影響範囲を絞れない |
